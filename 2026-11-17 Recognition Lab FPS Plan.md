## Current path and bottleneck candidates

Camera → video-frame callback → optional resize → hand inference → pose inference → hand assignment and upper-body sample → overlay and recognition observer → next frame request.

- The camera requests 1280 × 720 at an ideal 30 FPS. Compare the actual track settings and presented cadence with processed cadence. At 30 FPS a new source frame arrives about every 33 ms.
- The default Lab uses original input resolution, both models on the main thread, and a visible pose overlay. GPU is attempted independently for each model with CPU fallback. Both models run serially regardless of inference thread. The paired worker path adds bitmap creation/transfer and result serialization. It requests the next frame after main-thread handling of the prior result, so the pipeline can miss source frames while busy or idle between callbacks. Worker mode may improve responsiveness even with similar or lower throughput.
- The optional 640 px width reduces input with a reusable canvas. At 1280 × 720 the resulting 640 × 360 image has one quarter the pixels. Resize overhead, upload cost, and tracking quality determine the net result.
- Pose drawing and pose inference are separate. Hiding the skeleton still runs the pose model in Hands + pose mode. Both canvases use full video dimensions. Camera drawing issues individual strokes and fills per landmark or connection and reads a small brightness sample twice a second.
- Main-thread requestAnimationFrame fallback can process repeated media timestamps. The worker fallback already skips repeats. Count distinct source samples to avoid overstating gains.
- Active Lab recognition adds synchronous hand assignment and window/observation work plus result-driven React updates. Backend prediction is asynchronous on the camera path. Measure request round trips and confirmation delay separately from landmark throughput. Offline replay seeks and samples at a fixed 20 Hz in source time and awaits its observer. Measure wall-clock replay duration separately.
- Source verified on branch NF in the current working tree on Nov 17. The historical benchmarks below quantify stage costs. The reported current session still needs a benchmark with matched settings.

## Change order and decisions

1. Select the best existing configuration from the matrix. Prioritize stable fresh updates and low frame age. Use actual camera cadence as the target. Aim for close to one useful paired update per available frame during well-framed signing, with stable tracking and comparable recognition quality.
2. If rendering or observation drives stalls, batch canvas paths by style, evaluate a smaller overlay buffer, and coalesce React status/progress updates. Preserve sample delivery and sample timestamps for recognition. Verify visual alignment, mirroring and handedness colors.
3. If worker transport or scheduling drives gaps, benchmark transferring only the landmark fields consumed downstream and eliminate avoidable copies where supported. Evaluate keeping the newest available source frame while one request is in flight, with bounded work, stale-frame rejection and bitmap cleanup. Compare source-to-result age as well as throughput. Dedupe main-thread fallback samples if the benchmark confirms repeat processing. Check stop, restart, unmount and worker initialization/runtime failure.
4. If landmarker compute dominates, compare lower input resolutions and GPU/CPU combinations on actual hardware. Smaller hands and overlap are quality gates. If still limited, test a lower pose cadence as a separate experiment with pose-age limits and explicit alignment rules. Verify hand-side assignment, motion and sequence boundaries before considering it for recognition. Consider capture changes only if camera cadence or decode is the measured limit. Keep model/checkpoint selection fixed for these comparisons.
5. Promote a Lab candidate after repeated runs show better throughput or responsiveness without a material drop in landmarks or sign outcomes. Document device-specific results and retest on a second device if available. Roll out per caller after verifying Live Conversation confirmation and Collector timing, sample shape, export compatibility, and offline imports.
